# AI 中转站 2API 服务插件化架构调研与演进方案

> **调研背景**：当前中转站已先后接入 `aws-quickwork-2api`（+ `quick-autoreg`）、`muse2api`、`workbuddy2api` 三套独立 2API 能力。每新增一个 2API，目前仍需手工修改 `docker-compose.yml`、`.env`、Nginx 站点配置、`scripts/backup.sh` 以及 New API MySQL `channels` + `abilities` 表。  
> **核心问题**：能否把这些 2API 全部做成**可热插拔、统一声明、一键启停的插件式架构**？

---

## 一、 总结结论（双层解耦看本质）

| 插件化路径 | 能否覆盖现有全部 2API？ | 实测结论与适用边界 |
| :--- | :--- | :--- |
| **路径 A：New API 原生 JS 插件** (`v1.0.0-rc.51` 内置 `moejs` 运行时，Type-61 渠道) | **不能完全覆盖**（仅适合纯 HTTP 协议转换与异步视频/任务轮询） | `muse2api` 与 `quick-autoreg` 强依赖无头 Chromium + Playwright；`workbuddy2api` 与 `quickwork2api` 重度依赖 `utls` 指纹伪装、HTTPDNS、二进制 EventStream/WSS 与复杂 Web 批量上号面板，强行改写为无第三方库的沙箱 JS 成本极高甚至不可行。 |
| **路径 B：网关编排层插件化**（`Docker Compose include` + `Nginx conf.d/plugins` + `plugin.json` + `plugin.sh`） | **100% 全部适用**（零代码入侵上游 2API，兼容 Go/Python/Node/Playwright 任意技术栈） | **强烈推荐主方案**。本机实测服务器已是 **Docker Compose v5.8.0** + **Nginx 1.24.0** + **New API v1.0.0-rc.51**，完全原生支持模块化 `include` 编排、自动化渠道同步与控制台导航注入。 |

> **最佳实践**：采用 **“路径 B（网关底座插件化）”为主框架 + “路径 A（New API 原生 JS 插件）”为轻量化补充（如全局请求脱敏、自动推理档位、纯 HTTP 异步生图/生视频厂商）** 的混合插件架构。

---

## 二、 路径 A 深度核查：New API 原生 JS 插件系统（`moejs`）的能力边界

根据目前线上运行的 `calciumion/new-api:latest`（实测版本 **`v1.0.0-rc.51`**）及官方 `docs/plugin-api/v1.md` 规范：

### 1. New API 已原生支持的能力
- **Task Part + Provider Part（Type-61 渠道）**：不仅支持异步生图/生视频任务（官方插件市场已有 `sora`、`vidu`、`kling`、`jimeng`、`hailuo`、`alibaba` 等 19 个官方插件），还新增了 `meta.relay` 路由、OAuth `login`/`refresh`、`scheduled` 定时维护、`Upstream WebSocket` 以及请求处理钩子（`request-redact`、`auto-reasoning` 等）。
- **前端导航扩展点**：`/api/status` 已原生预留 `HeaderNavModules` 与 `SidebarModulesAdmin` 字段，可直接把外部面板链接或模块挂进 New API 后台侧边栏。

### 2. 为什么现有三大 2API **不适合** 全部重写进 `moejs`？

| 服务 | 核心依赖技术栈 | New API `moejs` 沙箱硬限制 | 结论 |
| :--- | :--- | :--- | :--- |
| **`muse2api`** | Headless Chromium + Playwright + CDP (`shm_size: 2gb`) + 本地媒体直链 `/v1/media/` + Chrome 导号扩展 | 纯 Go JS 沙箱，无子进程/浏览器引擎、无本地文件系统静态托管、单 Hook 限 **5 秒 CPU / 512 MiB 内存** | **不可行** |
| **`quick-autoreg`** | Playwright 无头浏览器自动化注册 AWS Builder ID | 同上，无法运行浏览器内核与 DOM 截图 | **不可行** |
| **`workbuddy2api`** | Go `utls`（逐项对齐官方桌面端 TLS 指纹防风控）、HTTPDNS 容错、Trae/Qoder 设备私钥签名、per-account 代理池、全套 React 运维面板（签到/猫猫旅行/成长任务） | `utils.fetch` 走宿主标准 TLS 栈无法自定义 JA3/HTTP2 指纹，不支持独立子代理池与持久化多文件账本，无第三方 Go/npm 库 | **不建议（会丢失核心抗风控与面板能力）** |
| **`quickwork2api`** | OAuth2 PKCE 本地回调 + AWS AIDP 二进制 EventStream over WSS + FNV-1a 粘性亲和 + `least-in-flight` 溢出 + `/quick-admin` 批量上号 UI | 虽支持 `Upstream WebSocket (dataBase64)`，但在单文件 ES JS 中手写 AWS 二进制 EventStream 帧编解码与粘性调度维护成本极高，且会丢失批量上号 UI | **性价比极低，不建议** |

---

## 三、 路径 B 落地方案：网关编排层标准化插件架构（100% 兼容）

把每一个 2API 能力封装为一个自包含目录 `plugins/<plugin-id>/`，彻底消除“每次加一个 2API 都要改 5~6 个核心文件”的耦合痛点。

### 1. 推荐目录结构

```text
/opt/llm-gateway/
├── docker-compose.yml              # 仅保留核心底座 (new-api, mysql, redis, uptime-kuma)
│                                   # 底部通过 include: 动态引入已启用插件的 compose.yml
├── plugins/
│   ├── quickwork/                  # 插件 1：AWS Quick + Autoreg
│   │   ├── plugin.json             # 声明元信息、内部端点、模型列表、分组、备份路径、面板路径
│   │   ├── compose.yml             # 声明 quickwork2api + quick-autoreg 服务
│   │   ├── nginx.conf.template     # 声明 /quick-admin 与 /quick-autoreg 路由片段
│   │   └── env.example
│   ├── muse/                       # 插件 2：Meta Muse 多模态
│   │   ├── plugin.json
│   │   ├── compose.yml
│   │   ├── nginx.conf.template     # 声明 /admin, /muse-admin, /v1/media/, /v1/images/tasks
│   │   └── env.example
│   └── workbuddy/                  # 插件 3：WorkBuddy / Trae / Qoder 多号池
│       ├── plugin.json
│       ├── compose.yml
│       ├── nginx.conf.template     # 声明 /wb-admin/ (含 rewrite + sub_filter)
│       └── env.example
├── nginx/
│   └── conf.d/
│       ├── 00-gateway-common.conf
│       ├── model.that-is-ai.com.conf   # server { ... include /etc/nginx/conf.d/model-plugins/*.conf; }
│       └── model-plugins/              # 仅存放已启用插件的符号链接或渲染后的 .conf
└── scripts/
    └── plugin.sh                   # 统一插件 CLI：list / enable / disable / sync-channels / backup
```

### 2. 核心设计要点（已验证可行性）

1. **Docker Compose 原生 `include:`（服务器实测 Compose `v5.8.0` 支持）**
   - 主 `docker-compose.yml` 只需维护一个自动生成的 `plugins/enabled.compose.yml` 或在主文件中引用：
     ```yaml
     include:
       - plugins/quickwork/compose.yml
       - plugins/muse/compose.yml
       - plugins/workbuddy/compose.yml
     ```
   - 每个插件内部服务统一接入外部/顶层 `gateway-net`，通过 `127.0.0.1:<port>:<container_port>` 仅向宿主机回环暴露，内部容器间直接用 `http://<service>:<port>` 通信。

2. **Nginx `include` 路由片段隔离（服务器实测 Nginx `1.24.0` 支持）**
   - 在 `model.that-is-ai.com.conf` 的 `server { ... }` 块内（`location /` 兜底之前）加入一行：
     ```nginx
     include /etc/nginx/conf.d/model-plugins/*.conf;
     ```
   - 启用插件时自动把 `plugins/<id>/nginx.conf.template` 链接/复制到 `/etc/nginx/conf.d/model-plugins/<id>.conf` 并执行 `nginx -t && systemctl reload nginx`；禁用时移除文件并重载，**互不干扰**。
   - **子路径统一约定**：推荐新插件面板统一挂载到 `/plugins/<id>-admin/` 或 `/<short>-admin/`（如 `/quick-admin`、`/muse-admin`、`/wb-admin/`），对前端静态写死 `/panel/` 的开源镜像（如 `workbuddy2api-panel`），在插件的 `nginx.conf` 中统一用 `proxy_set_header Accept-Encoding ""; sub_filter '/panel/' '/wb-admin/';` 零修改上游镜像即可适配。

3. **标准 `plugin.json` 清单 + 自动同步 New API 渠道**
   ```json
   {
     "id": "workbuddy",
     "name": "WorkBuddy-Pool",
     "admin_path": "/wb-admin/",
     "channel": {
       "type": 1,
       "base_url": "http://workbuddy2api:7863",
       "api_key_env": "WB2A_API_KEY",
       "test_model": "deepseek-v4-flash",
       "groups": ["default", "free_fans", "vip_official"],
       "models": ["deepseek-v4", "deepseek-v4-flash", "glm-5.3", "glm-5.2", "kimi-k2.5"]
     },
     "backup_paths": [
       "workbuddy2api/auths",
       "workbuddy2api/config.json",
       "workbuddy2api/data/state.json",
       "workbuddy2api/data/api_keys.json",
       "workbuddy2api/data/providers.json",
       "workbuddy2api/data/proxies.json"
     ]
   }
   ```
   - `scripts/plugin.sh sync-channels` 读取所有已启用插件的 `plugin.json`，自动幂等写入/更新 New API 的 `channels` 与 `abilities` 表（并通知或重启加载缓存），禁用插件时自动将对应渠道置为 `status=2`（禁用）而不删历史账单。
   - `scripts/backup.sh` 遍历所有已启用插件的 `backup_paths` 自动归档加密上传 Cloudflare R2，不再需要每次手动改备份脚本。

4. **统一运维导航（告别记忆一堆端口和 `?key=`）**
   - 利用 **New API 自带的 `SidebarModulesAdmin` / `HeaderNavModules`**（已在 `/api/status` 验证存在）或新增一个轻量的静态聚合页 `/ops/`（受 Nginx Basic Auth 或管理员 Token 保护），自动根据已启用插件的 `plugin.json` 生成卡片入口，一键跳转：
     - **AWS Quick 号池 & 自动注册**（`/quick-admin` & `/quick-autoreg`）
     - **Meta Muse 多模态工作台**（`/admin` / `/muse-admin`）
     - **WorkBuddy 多号池管理面板**（`/wb-admin/`）

## 四、 演进实施路线建议

1. **阶段一（当前已完成）**：`quickwork2api`、`quick-autoreg`、`muse2api`、`workbuddy2api` 均已通过标准 Docker 容器 + 回环端口 + Nginx 隔离反代 + New API 渠道 + `backup.sh` 多号池归档跑通生产环境。
2. **阶段二（平滑插件化改造，零停机）**：在不改变现有数据目录（`aws-quickwork-2api/data`、`muse2api/data`、`workbuddy2api/{auths,data}`）的前提下，抽离 `plugins/{quickwork,muse,workbuddy}` 清单与 `scripts/plugin.sh`，并将 Nginx 拆分为 `model-plugins/*.conf`。
3. **阶段三（New API 原生插件补充）**：对纯 HTTP 协议的通用增强能力（如自动思考档位、提示词脱敏）或商业化视频 API（Sora/Vidu/Kling），直接通过 New API 后台「插件市场」安装原生 `moejs` 插件，与自托管 2API 容器插件互补共存。
